# 1.1 — Live Rig (footswitch performance package)

Status: **tracked for 1.1, not started.** 1.0 ships unchanged. Board task #123.
Sibling of the other 1.1 item, the session-portability bundle (#116).

The target rig: a **Morningstar MC8 Pro** (8 footswitches, paged) driving the synth's
looper + scenes hands-free, plus a **Focusrite Scarlett** feeding external audio into the
loop lanes. This package turns the synth from a desktop instrument into a standalone
live looping rig.

## What already works in 1.0 (no code — documented in the README MIDI-mapping section)
- Every looper lane's **REC** (`loop_rec` … `loop_rec4`) and **PLAY** (`loop_play` … `loop_play4`)
  is MIDI-learnable (right-click / long-press the button, send the CC).
- A learned CC sets the value to `cc/127`, so a **bool toggle reads 127 = on, 0 = off**
  (absolute, not a latch). Footswitches must send a **Toggle CC** (alternating 127/0) to latch.
- Use CCs in the undefined **102–119** range to avoid the Launchkey macro defaults (21–28), CC1, CC64.

That covers a four-lane record/mute rig on release day. Everything below is the 1.1 build.

## Spec 1 — MIDI scene control

Scenes (`launchScene(i)`, J3) are UI-only today: they aren't APVTS params, so MIDI-learn
can't reach them. Add a **first-class MIDI scene control path** with two modes, both honoring
the existing launch quantum (`scene_quant`) and the pending/edge rules already in J3.

- **Absolute — scene 1–8 direct.** Listen (on a configurable "control" channel) for either
  **Program Change 0–7** *or* **notes** (a contiguous 8-note block, base note configurable) →
  `launchScene(n)`. PC is the MC8-friendly default; notes are the alt for note-only controllers.
- **Relative — next / prev.** Two CCs (`scene_next`, `scene_prev`) that step the *armed* target
  up/down. Any 127 press advances the pending target.
- **Pending-target queue stacking.** Today a second tap re-arms (replaces) the pending scene.
  For a relative pedal you want to **queue-stack**: repeated next presses walk the pending target
  forward (1→2→3) while still unlaunched, all resolving at the next quantum boundary. Decision to
  pin at build: does "next" wrap (8→1)? Default **clamp**, not wrap (a footgun on stage).
- **Feedback.** The MC8 has no screen feedback from us unless we send MIDI back. Optional: emit a
  scene-changed message (PC echo or a CC) on the clock-out port so the controller LEDs can track
  the *active* (not pending) scene. Flag: reuse the #85 clock-out port or a separate virtual port?

Routing note: this must NOT collide with the surface/keyboard routing — the control channel is a
dedicated channel that is *consumed* (not forwarded to a part). Add to `MidiProfile` as a
`controlChannel` (0 = off), parsed like `padChannel`.

Tests: PC 0–7 → correct scene armed + engages at quantum; next/prev stacking resolves to the
right scene; control-channel messages never leak to a part's voices; goldens unaffected (feature
off by default until a profile enables it).

## Spec 2 — External audio input loop lanes (Scarlett → lane capture)

Today the 4 audio-loop lanes capture the **internal** per-part post-FX bus. 1.1: let a lane
capture an **external input channel** (a Scarlett input) so you can loop a guitar/vocal/synth.

- **Source select per lane.** Each lane gains a source: `Internal (part N)` (today) or
  `Ext In k` (a hardware input channel). The standalone already opens an input device; expose its
  channels. In a DAW, the plugin's sidechain/aux inputs are the source.
- **Monitoring.** Live input must be audible while playing *and* while the loop plays back —
  with a **monitor on/off + level** per lane (direct-monitor vs through-the-plugin). Flag: prefer
  hardware direct monitor on the Scarlett (zero latency) and keep the plugin path for the recorded
  loop only? Or offer software monitoring with the caveat below.
- **Latency compensation (DESIGN QUESTION — must resolve before build).** A recorded external
  loop must line up with the internal clock. The captured audio arrives late by
  `input_latency + buffer + output_latency`; the loop write position must be **offset by the
  round-trip latency** so overdubs stack in phase. Open questions to answer at build:
  1. Measure round-trip latency how — from the device manager's reported input+output latency, or
     a calibration ping (play a click, capture it, measure the offset)? Reported values are often
     wrong under PipeWire; a one-time calibration is more honest.
  2. Where to apply the offset — shift the write head at capture, or shift on playback? (Capture-side
     is cleaner for overdubs.)
  3. What about monitoring latency vs recording latency — they differ; the *player* hears direct
     monitor (0), but the *recording* is delayed. The comp only applies to the recorded stream.
  Ship v1 with a **manual latency-offset knob (ms) per rig** + a calibration helper, rather than
  guessing an automatic value.
- **Memory.** External audio lanes reuse the existing `kMaxLoopSeconds` rings — no new allocation.

Tests: an injected known input signal, looped, lines up sample-accurately after applying a known
offset; monitor on/off gates the live path but never the recorded loop; input-source select
persists in the rig/MULTI.

## Spec 3 — Drum fill engine

One-shot fills triggered from a footswitch, so a pedal press drops a fill and the groove returns.

- **Trigger.** A CC (`drum_fill`, 127) arms a fill; it **engages at the next measure boundary**
  (bar-quantized like scenes), plays for one bar (configurable 1/2 or 1 bar), then **auto-returns
  to the main step-sequencer pattern** the following measure. No latching — it's a momentary one-shot.
- **Fill content (v1 decision).** Two options, pick at build:
  - **Seeded random fills (v1, recommended first cut):** generate a fill from the current kit +
    a density/intensity param, using the project's own deterministic PRNG (same discipline as the
    WT randomizer — no `std` distributions, reproducible, committed golden). Zero UI.
  - **Small fill editor:** a handful of authored 1-bar fill patterns per kit (a mini step grid),
    selectable. More work; defer to v2 of this spec unless the seeded fills feel too random.
- **Interaction with scenes/seq.** A fill overlays the *drum part* only; it must not disturb the
  looper lanes or other parts, and must restore the exact prior pattern + step position after the
  fill bar (save/restore the seq play-head, like the scene edge rule).
- **Stuck-note safety.** Standing rule: engaging/disengaging a fill mid-note flushes held drum
  notes (the transition-stuck-notes regression criterion applies).

Tests: CC fill engages on the next bar, plays one bar, returns to the exact prior pattern; seeded
fill is bit-identical across platforms (golden); no cross-part leakage; no stuck notes on entry/exit.

## Spec 4 — MC8 Pro factory layout (documented)

Ship a documented, importable MC8 Pro layout matching the 8-switch design, plus a synth-side
MIDI-learn map (a device profile) so it's plug-and-play.

**8-switch page (the performance page):**

| Switch | Tap (press) | Long-press |
|--------|-------------|------------|
| 1 | Loop 1 REC (toggle CC) | Loop 1 PLAY/mute (toggle CC) |
| 2 | Loop 2 REC | Loop 2 PLAY/mute |
| 3 | Loop 3 REC | Loop 3 PLAY/mute |
| 4 | Loop 4 REC | Loop 4 PLAY/mute |
| 5 | Play/Stop ALL (4× PLAY toggle, multi-message) | — |
| 6 | Page nav (MC8 internal) | — |
| 7 | Scene NEXT (`scene_next`) | Scene PREV (`scene_prev`) |
| 8 | Drum FILL (`drum_fill`) | Scene 1 direct (PC 0) — "return to top" |

CC assignments live in the undefined 102–119 range; Toggle-type where a latch is needed
(all REC/PLAY), momentary 127 where one-shot (fill, scene next/prev/direct). The deliverable is
(a) an MC8 `.json`/backup export the user imports in morningstar.io/editor, and (b) a matching
synth **device profile** (`MidiProfile`) so the CCs auto-map on connect (precedence: user-learned
> this profile > factory, per the existing profile rule).

## Build order (proposed)
1. Spec 1 (scene MIDI) — smallest, highest value, unblocks the pedal's "sections".
2. Spec 4 (MC8 layout + device profile) — makes 1 + the existing looper CCs turn-key.
3. Spec 3 (fill engine, seeded v1) — self-contained on the drum part.
4. Spec 2 (external audio lanes) — biggest, has the open latency questions; do last.

Each is independently gated (`run-all-checks.sh` ± `--sanitize`, goldens bit-identical, feature
off by default until a profile/param enables it) and CI-green on both platforms before the next.
